# 语音录入问题的修复

## 一、问题清单

| # | 问题 | 严重程度 | 状态 |
|---|------|---------|------|
| 1 | 浏览器 MediaRecorder 输出 webm/opus，Baidu ASR 需要 pcm | 致命 | 确认 |
| 2 | 前端声明 sampleRate=48000，Baidu 期望 16000 | 致命 | 确认 |
| 3 | WebSocket connect() 异步，未等待连接完成就录音 | 中等 | 确认 |
| 4 | 一次性发送整个 blob，Baidu ASR 可能超时或拒绝 | 中等 | 确认 |
| 5 | 后端无 webm→pcm 转换，音频原样转发给 Baidu | 致命 | 确认 |
| 6 | 浏览器麦克风权限弹窗可能被阻止 | 低 | 可能 |
| 7 | Baidu API Key 配置错误导致 token 获取失败 | 低 | 可能 |

### 问题详细说明

#### P0：音频格式不匹配（最可能导致「识别中」卡住）

| 项 | 前端发送 | 后端期望 | 问题 |
|---|---------|---------|------|
| 格式 | webm（浏览器 MediaRecorder opus 编码） | pcm | Baidu ASR 不支持浏览器原生 webm/opus 格式 |
| 采样率 | 48000 | 16000 | 声明采样率与实际不一致 |

**后果：** 后端将 webm 音频原样发给 Baidu ASR → Baidu 返回 err_no != 0（格式错误）→ 后端发 error 消息 → 前端 fallbackToMock() → 但用户看到的是「识别中」卡住（中间结果已显示，mock 延迟才触发）

#### P1：WebSocket 连接竞态

| 问题 | 说明 |
|------|------|
| connect() 是异步的 | startRecording() 中调用 connect() 后立即开始录音，不等待连接建立 |
| sendToASR() 检查 wsStatus === 'open' | 如果连接未完成 → 跳过 WebSocket → 直接走 mock（用户看到假数据） |

#### P2：一次性发送 vs 流式

| 问题 | 说明 |
|------|------|
| 录音停止后一次性发送整个 blob | Baidu ASR 更适合流式输入，一次性大文件可能超时或被拒 |

#### P3：后端无格式转换

BaiduAsrService.java 是纯透传服务，不做任何音频格式转换。webm 数据原样发给 Baidu API，Baidu 无法解析则返回错误。

---

## 二、解决方案

### 核心思路

前端 Web Audio API 采集 PCM → WebSocket 流式发送

企业级项目（科大讯飞开放平台、百度语音 Demo、微信语音输入）的标准做法：

**不使用 MediaRecorder**，改用 AudioContext + ScriptProcessorNode 直接从麦克风采集 16kHz 16bit 单声道 PCM 原始数据，通过 WebSocket 流式发送到后端。

### 方案架构

```
浏览器                              后端                    Baidu ASR
  │                                  │                        │
  │  getUserMedia(麦克风)             │                        │
  │  AudioContext.createMediaStream  │                        │
  │  ScriptProcessorNode             │                        │
  │    ↓ 采集 PCM 16kHz 16bit        │                        │
  │  int16Array (每帧 1024 samples)  │                        │
  │                                  │                        │
  │ ── WebSocket send(pcm_chunk) ──→ │                        │
  │ ── WebSocket send(pcm_chunk) ──→ │  转发给 Baidu          │
  │ ── WebSocket send(pcm_chunk) ──→ │  ─────────────────→   │
  │                                  │                        │
  │                                  │ ←─ 中间结果 ──────── │
  │ ←── intermediate_result ──────── │                        │
  │                                  │                        │
  │  停止录音                         │                        │
  │ ── WebSocket send(end) ────────→ │                        │
  │                                  │ ←─ 最终结果 ──────── │
  │ ←── final_result ─────────────── │                        │
```

### 具体改动

#### 前端改动（useVoice.ts 重构）

| 改动 | 说明 |
|------|------|
| ScriptProcessorNode 替代 MediaRecorder | 直接采集 PCM float32 数据 |
| Float32 → Int16 转换 | Baidu 需要 16bit PCM |
| 重采样 48kHz → 16kHz | 浏览器默认 48kHz，Baidu 需要 16kHz |
| 流式发送 | 每 100ms 发送一帧 PCM，而非录音结束后一次性发送 |
| WebSocket 先连接再录音 | await connect() 后再 getUserMedia |
| 消息协议 | {type:"start"}, {type:"audio", data:"base64"}, {type:"end"} |

#### 后端改动（VoiceWebSocketHandler 适配）

| 改动 | 说明 |
|------|------|
| 接收 start 消息 | 初始化 ASR 会话，记录 format/采样率 |
| 接收 audio 消息 | 累积 PCM 数据到缓冲区 |
| 接收 end 消息 | 将累积的 PCM 数据一次性发给 Baidu ASR |
| 返回中间/最终结果 | 沿用现有 intermediate_result / final_result 协议 |

### 依赖

| 依赖 | 说明 |
|------|------|
| 前端：无额外依赖 | Web Audio API 是浏览器原生 API |
| 后端：无额外依赖 | 不需要 FFmpeg，PCM 数据直接转发 Baidu |

### 降级策略

| 条件 | 降级方案 |
|------|---------|
| 浏览器不支持 ScriptProcessorNode | 使用 MediaRecorder + 后端转换（需加 FFmpeg） |
| WebSocket 连接失败 | 降级到 mock ASR |
| Baidu ASR 失败 | 降级到 mock ASR |
| 麦克风权限被拒 | 提示用户开启权限 |

### 优势对比

| 方案 | 延迟 | 复杂度 | 兼容性 | 企业采用 |
|------|------|--------|--------|---------|
| 前端 PCM 采集 + WS 流式 | 低 | 中 | 高 | 百度Demo、讯飞、微信 |
| MediaRecorder + 后端 FFmpeg 转码 | 中 | 高（需装 FFmpeg） | 高 | 传统方案 |
| MediaRecorder + 前端 decodeAudioData | 中 | 中 | 中 | 一般 |
| 保持现状（webm 直传） | - | - | - | 不可用 |
