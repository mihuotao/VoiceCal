# VoiceCal - 智能语音日历

## 项目架构说明文档 v1.0

---

## 📌 一、项目简介

VoiceCal 是一款基于语音交互的智能日历，通过集成百度云语音服务，实现语音创建、查询、修改、删除日程，并提供智能冲突检测与排期建议，帮助用户高效管理时间。

---

## 🏗️ 二、系统架构

### 2.1 整体架构

VoiceCal 采用前后端分离的单体架构，通过 WebSocket 实现实时语音通信，结合 Redis 缓存提升性能，使用 Docker 容器化部署保障环境一致性。

```
┌─────────────────────────────────────────────────────────────────────┐
│                          用户终端层                                  │
│                     浏览器 (Chrome / Edge)                          │
│  ┌─────────────┐    ┌─────────────┐    ┌─────────────┐             │
│  │  语音交互   │    │  日历展示   │    │  消息通知   │             │
│  └─────────────┘    └─────────────┘    └─────────────┘             │
└─────────────────────────────────────────────────────────────────────┘
                                  │
                           HTTPS / WSS
                                  ▼
┌─────────────────────────────────────────────────────────────────────┐
│                          接入层                                     │
│                    Nginx (反向代理 + SSL)                           │
└─────────────────────────────────────────────────────────────────────┘
                                  │
                                  ▼
┌─────────────────────────────────────────────────────────────────────┐
│                        应用服务层                                    │
│               Spring Boot 3.2 (单体应用)                           │
│  ┌───────────────────────────────────────────────────────────────┐  │
│  │  接口层: RESTful API + WebSocket Endpoint                    │  │
│  ├───────────────────────────────────────────────────────────────┤  │
│  │  业务层: 日历服务 / 语音服务 / NLU服务 / 排期服务             │  │
│  ├───────────────────────────────────────────────────────────────┤  │
│  │  数据层: JPA + Redis Cache                                   │  │
│  └───────────────────────────────────────────────────────────────┘  │
└─────────────────────────────────────────────────────────────────────┘
                    │                    │                    │
                    ▼                    ▼                    ▼
          ┌─────────────┐    ┌─────────────┐    ┌─────────────┐
          │    MySQL    │    │    Redis    │    │  百度云API  │
          │   持久化    │    │    缓存     │    │  语音服务   │
          └─────────────┘    └─────────────┘    └─────────────┘
```

### 2.2 部署架构

采用 Docker Compose 容器化部署，实现一键启动、环境隔离、易于扩展：

```
Docker Compose 编排
├── nginx        :80/:443    反向代理
├── frontend     :5173       Vue 3 前端
├── backend      :8080       Spring Boot 后端
├── mysql        :3306       数据库
└── redis        :6379       缓存服务
```

## 💡 四、创新点说明

### 4.1 流式语音实时识别

**传统方式**：用户说完 → 等待识别 → 返回结果（延迟 2-3 秒）

**创新方式**：边说边识别，实时显示中间结果（延迟 <500ms）

```
技术实现：
┌─────────────┐    音频流     ┌─────────────┐    流式识别    ┌─────────────┐
│   前端录音   │ ──────────→ │  WebSocket  │ ──────────→ │  百度云ASR  │
│  (200ms/片) │             │   Server    │             │  (流式模式) │
└─────────────┘             └─────────────┘             └─────────────┘
                                  │
                                  │ 实时推送中间结果
                                  ↓
                            ┌─────────────┐
                            │  前端实时显示 │
                            │  识别文本    │
                            └─────────────┘
```

**价值与优势**：

| 维度   | 传统方式  | 创新方式   |
| ---- | ----- | ------ |
| 交互延迟 | 2-3 秒 | <500ms |
| 用户体验 | 等待焦虑  | 实时反馈   |
| 纠错成本 | 说完才能改 | 边说边改   |
| 流畅度  | 断续感强  | 自然流畅   |

**技术实现细节**：

- 前端：MediaRecorder API 每 200ms 采集一帧 PCM 音频
- 传输：WebSocket 二进制帧实时推送
- 后端：转发至百度云流式 ASR API
- 识别：百度云端边接收边识别，返回中间结果
- 回传：识别结果通过 WebSocket 实时推送回前端

### 4.2 多轮对话式日程管理

**传统方式**：每次语音命令都是独立的单轮交互

**创新方式**：支持上下文感知的多轮对话

```
示例对话：
用户：添加明天下午的会议
系统：好的，请问会议时间和主题是什么？
用户：3点，项目评审
系统：已添加"项目评审"，明天下午3点。需要设置提醒吗？
用户：提前15分钟提醒
系统：好的，已设置提前15分钟提醒。
```

**价值与优势**：

| 维度    | 传统方式      | 创新方式      |
| ----- | --------- | --------- |
| 输入效率  | 一句话说完所有信息 | 分步补充，自然表达 |
| 容错性   | 说错必须重来    | 逐步确认，随时修正 |
| 学习成本  | 记忆固定命令格式  | 自然对话即可    |
| 交互自然度 | 机械指令式     | 人机对话式     |

**技术实现细节**：

- 前端：维护对话上下文栈（最近3轮）
- 后端：NLU 引擎解析省略信息
  - 检测意图缺失 → 追问
  - 检测实体缺失 → 追问
- 状态机：IDLE → COLLECTING → CONFIRMING → EXECUTING

### 4.3 智能时间表达解析

**传统方式**：只支持标准时间格式（如"2024-03-15 15:00"）

**创新方式**：支持自然语言时间表达

```
支持的时间表达：
├── 绝对时间
│   ├── "明天下午3点"
│   ├── "下周五上午10点半"
│   └── "3月15号"
├── 相对时间
│   ├── "三天后"
│   ├── "下周"
│   └── "月底"
├── 模糊时间
│   ├── "找个时间和小王吃饭"
│   └── "这周有空的时候"
└── 周期时间
    ├── "每周一上午9点"
    └── "每月1号"
```

**价值与优势**：

| 维度   | 传统方式                    | 创新方式          |
| ---- | ----------------------- | ------------- |
| 输入格式 | 固定格式 "2024-03-15 15:00" | 自然语言 "明天下午3点" |
| 学习成本 | 需要记忆格式                  | 日常说话即可        |
| 灵活性  | 只支持精确时间                 | 支持模糊、相对、周期    |
| 智能程度 | 无                       | 理解上下文         |

**技术实现细节**：

解析引擎结构：

- 绝对时间解析器：正则匹配 + 日期库转换
- 相对时间解析器：基于当前日期 + 偏移计算
- 模糊时间解析器：关键词识别 + 默认值填充
- 周期时间解析器：重复规则生成器

示例解析流程："下周三下午3点"
→ 识别：相对时间 + 星期 + 时段 + 小时
→ 计算：当前日期 + 7天 → 找到下周三 → 15:00
→ 输出：2026-06-04 15:00:00

### 4.5 智能冲突检测与排期

**传统方式**：用户手动检查时间冲突

**创新方式**：自动检测冲突并推荐最优排期

```
冲突检测流程：
┌─────────────────────────────────────────────────────────────┐
│  输入：新事件 (startTime, endTime, location)                │
└─────────────────────────┬───────────────────────────────────┘
                          │
                          ▼
┌─────────────────────────────────────────────────────────────┐
│  Step 1: 时间冲突检测                                       │
│  查询条件：同一用户 + 状态active + 时间重叠                  │
│  重叠判断：existing.start < new.end AND existing.end > new.start│
└─────────────────────────┬───────────────────────────────────┘
                          │
                          ▼
┌─────────────────────────────────────────────────────────────┐
│  Step 2: 冲突分级                                           │
│  ├── 完全冲突：时间完全重叠                                  │
│  ├── 部分冲突：时间部分重叠                                  │
│  └── 紧密相邻：间隔 < 15分钟                                 │
└─────────────────────────┬───────────────────────────────────┘
                          │
                          ▼
┌─────────────────────────────────────────────────────────────┐
│  输出：冲突列表 + 冲突级别 + 解决建议                        │
└─────────────────────────────────────────────────────────────┘
```

```
智能排期流程：
┌─────────────────────────────────────────────────────────────┐
│  输入：待安排事件列表 + 时间范围 + 用户偏好                  │
└─────────────────────────┬───────────────────────────────────┘
                          │
                          ▼
┌─────────────────────────────────────────────────────────────┐
│  Step 1: 收集约束条件                                       │
│  ├── 已有日程（不可移动）                                    │
│  ├── 用户偏好（工作时间、休息时间）                          │
│  └── 事件优先级                                             │
└─────────────────────────┬───────────────────────────────────┘
                          │
                          ▼
┌─────────────────────────────────────────────────────────────┐
│  Step 2: 生成可用时间段                                     │
│  ├── 遍历日期范围                                           │
│  ├── 排除已有日程占用的时间                                  │
│  └── 生成空闲时间段列表                                      │
└─────────────────────────┬───────────────────────────────────┘
                          │
                          ▼
┌─────────────────────────────────────────────────────────────┐
│  Step 3: 事件匹配与评分                                     │
│  ├── 按优先级排序事件                                        │
│  ├── 高优先级事件优先安排在黄金时间                          │
│  └── 生成多个备选方案 + 评分                                 │
└─────────────────────────┬───────────────────────────────────┘
                          │
                          ▼
┌─────────────────────────────────────────────────────────────┐
│  输出：推荐排期方案 + 备选方案 + 排期评分                    │
└─────────────────────────────────────────────────────────────┘
```

**价值与优势**：

| 维度    | 手动管理  | 智能排期      |
| ----- | ----- | --------- |
| 冲突发现  | 容易遗漏  | 自动检测      |
| 时间规划  | 凭感觉安排 | 数据驱动优化    |
| 决策效率  | 反复权衡  | 一键推荐      |
| 时间利用率 | 低     | 高（黄金时间优先） |

**技术实现细节**：

冲突检测算法：

- 时间重叠判断：existing.start < new.end AND existing.end > new.start
- 冲突分级：
  - 完全冲突：重叠 > 90%
  - 部分冲突：重叠 10%-90%
  - 紧密相邻：间隔 < 15分钟

智能排期算法：

1. 生成空闲时间段（排除已有日程）
2. 按优先级排序待安排事件
3. 匹配最优时间段（评分规则）：
   - 上午黄金时间 (9-11点)：+10分
   - 下午黄金时间 (14-16点)：+8分
   - 午休时间 (12-13点)：+3分
   - 其他时间：+5分
4. 生成多个备选方案
5. 返回评分最高的方案

### 4.6 跨平台/多设备同步

**传统方式**：日历数据分散在不同设备，无法同步，换设备需要重新录入

**创新方式**：一个账号，多端同步，数据实时一致

└──────┬──────┘     └──────┬──────┘     └──────┬──────┘
       │                   │                   │
       └───────────────────┼───────────────────┘
                           │
                    统一 API + JWT
                           │
                           ▼
                  ┌─────────────────┐
                  │  Spring Boot    │
                  │  (统一后端)     │
                  └────────┬────────┘
                           │
                           ▼
                  ┌─────────────────┐
                  │  MySQL + Redis  │
                  │  (统一数据源)   │
                  └─────────────────┘
                           │
                    未来扩展入口
                           │
       ┌───────────────────┼───────────────────┐
       │                   │                   │
       ▼                   ▼                   ▼
┌─────────────┐     ┌─────────────┐     ┌─────────────┐
│  微信小程序  │     │   App       │     │  桌面客户端  │
│  (uni-app)  │     │ (Flutter)   │     │ (Electron)  │
└─────────────┘     └─────────────┘     └─────────────┘
```

**价值与优势**：

| 维度    | 单设备  | 跨平台同步 |
| ----- | ---- | ----- |
| 数据可用性 | 仅本设备 | 随时随地  |
| 设备切换  | 重新录入 | 无缝衔接  |
| 数据安全  | 依赖本地 | 云端备份  |
| 扩展性   | 有限   | 无限扩展  |

**技术实现细节**：

核心设计原则：

- 数据云端化：MySQL 统一存储，不依赖本地
- API 通用化：RESTful 设计，不绑定平台
- 认证标准化：JWT 多端同时在线
- 通信实时化：WebSocket 多端同步推送

未来扩展路径：

```
Web → 微信小程序 (uni-app)
    → 移动 App (Flutter/React Native)
    → 桌面客户端 (Electron)
